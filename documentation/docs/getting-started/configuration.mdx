# OPAL Configuration Guide

## Getting Started with OPAL Configuration

OPAL supports multiple ways to configure your deployment:

- **Environment Variables** (recommended) - `export OPAL_SERVER_URL=http://localhost:7002`
- **Command Line Arguments** - `opal-server run --server-url http://localhost:7002`
- **Configuration Files** - `.env` or `.ini` files in your project

### Essential Configuration

Let's get OPAL running! You'll need to set a few environment variables that tell OPAL where to find your policies and how to connect everything together.

#### OPAL Server
```bash
# Where your policies are stored (Git repo)
export OPAL_POLICY_REPO_URL=https://github.com/your-org/policy-repo.git

# Where clients get initial data
export OPAL_DATA_CONFIG_SOURCES='{
  "config": {
    "entries": [{
      "url": "http://localhost:7002/policy-data",
      "topics": ["policy_data"],
      "dst_path": "/static"
    }]
  }
}'

# Broadcast channel for scaling (use Redis or PostgreSQL)
export OPAL_BROADCAST_URI=postgres://postgres:postgres@localhost:5432/postgres
```

#### OPAL Client
```bash
# Connect to your OPAL server
export OPAL_SERVER_URL=http://localhost:7002

# Authentication token (change in production!)
export OPAL_CLIENT_TOKEN=your-secret-token

# Policy engine type (OPA is default, Cedar also available)
export OPAL_POLICY_STORE_TYPE=opa
```

### Production Configuration

When you're ready to deploy to production, you'll need to configure a few more things to ensure security and reliability.

- **Use HTTPS** for all OPAL server communication
- **Generate strong cryptographic keys** for JWT authentication
- **Store secrets securely** (never commit to repositories)
- **Use webhooks** instead of polling for policy updates

#### OPAL_SCOPES_REPO_CLONES_SHARDS

Default: `1`

The max number of local clones to use for the same repo (reused across scopes).

#### OPAL_SCOPES_GIT_FETCH_TIMEOUT

Default: `120.0`

Soft timeout in seconds for a single scope git clone/fetch: the awaiting operation is abandoned (the event loop and the sync pass move on) and the op is logged and skipped, retried next cycle. It is a SOFT timeout: the underlying git call keeps running on its own thread, and the pinned libgit2 sets no socket/server read timeout, so a black-holed remote can keep that thread — and the source's in-flight marker — alive for the life of the process (that source is then skipped until it recovers or the process restarts); SCOPES_GIT_MAX_ZOMBIES bounds how many such threads accumulate. Either way one unreachable repo never blocks boot or other scopes (0 = no timeout). With SCOPES_GIT_FETCH_WITH_CLI on it is a HARD timeout instead: git is stopped at the timeout (see SCOPES_GIT_CLI_KILL_GRACE).

#### OPAL_SCOPES_GIT_FETCH_WITH_CLI

Default: `False`

Whether scope fetches and clones run the git command line (git fetch) instead of libgit2. A libgit2 fetch runs on a thread that cannot be stopped, so one that hangs keeps its clone from syncing until it returns or the process restarts. With this on each op runs git in a process group of its own, and SCOPES_GIT_FETCH_TIMEOUT is hard: at the timeout the group gets SIGTERM, then SIGKILL SCOPES_GIT_CLI_KILL_GRACE seconds later, the lock files and partial pack git left in the clone are removed, and the next sync fetches the clone again. The group also ends itself when the server process that started it dies. Each op holds a lock on its clone (the file `.SOURCE_ID.lock` beside it) that git's group inherits, so no other op, repack or cleanup touches the clone while any of the op's processes lives; a sync that finds a clone locked skips it and counts opal_server.scopes.git_op_skipped (reason clone_busy). What an op that ended early left in its clone is removed by the next op on that clone, and by the pre-fork scope preload for every clone, with this on or off. Remote timeouts and failures are logged, counted and backed off as libgit2's are; failures on the server's own side (no git, a clone that cannot be set up, an unreadable SCOPES_GIT_SSH_KNOWN_HOSTS) are logged at ERROR and counted with reason `local`, without backoff. A source whose URL or credentials cannot be given to git without a credential on its command line or in what it prints is logged and counted the same way, and backed off as well, since only a change of the source fixes it. A new clone is fetched into a directory beside its final path and renamed into place once complete. A clone keeps what the scopes fetcher reads from a libgit2 clone (the same remote, its `refs/remotes/<remote>/*` refs, a FETCH_HEAD rewritten only by a fetch that succeeded), so this can be switched either way without cloning again, and bundles are built from it as before; a clone made by git has no checkout, which nothing reads. Fetches skip tags and prune when SCOPES_GIT_FETCH_PRUNE is on. As libgit2, git reads neither the system's nor the user's git config, runs no hooks, speaks only http, https, ssh, git and file, and uses no proxy; the CA certificates of SSL_CERT_FILE and SSL_CERT_DIR reach it as GIT_SSL_CAINFO and GIT_SSL_CAPATH. Credentials reach git through its environment, for http(s) through a credential helper that answers only for the source's own host, or, for an SSH key, a file only the server's user can read, removed when the op ends; never through its command line. git speaks protocol v2, whatever a clone's own config says, and ssh gives up on a connect after 30 seconds and on a link the server stays silent on after about a minute (4 keepalives, 15 seconds apart, unanswered), with an error of its own rather than at the timeout. Each op forks the server process, which under uvloop costs about 40 ms at 1.5 GB of resident memory. Needs git 2.32 or later on PATH, /bin/sh (git runs under it, which reports git's exit status), and ssh for SSH sources; the official images, Debian and Alpine, have all three, and the server does not start without git 2.32 or /bin/sh. SSH host keys: see SCOPES_GIT_SSH_KNOWN_HOSTS.

#### OPAL_SCOPES_GIT_CLI_KILL_GRACE

Default: `5.0`

With SCOPES_GIT_FETCH_WITH_CLI on: seconds a git fetch or clone that ran past SCOPES_GIT_FETCH_TIMEOUT gets to exit on SIGTERM, which lets git remove its own lock files and temporary pack, before its process group gets SIGKILL. OPAL then waits up to 10 seconds more for the group to exit, and once it has, removes what git left in the clone (for a clone, its partial directory) before the op ends. The timeout counts from git's start, after the op has taken the clone's lock and removed what an earlier op left, so an op ends at most this plus 10 seconds, plus that removal, past its timeout. A git stuck in uninterruptible I/O even after SIGKILL keeps its clone from being synced until it exits, as a hung libgit2 fetch does. 0 sends SIGKILL at once. With SCOPES_GIT_FETCH_WITH_CLI on, the server does not start when this is negative, nan or inf.

#### OPAL_SCOPES_GIT_SSH_KNOWN_HOSTS

Default: `None`

With SCOPES_GIT_FETCH_WITH_CLI on: the path of a known_hosts file to verify the git host's SSH key against. When set, a scope fetch or clone over SSH goes ahead only if the host's key is in this file (ssh's StrictHostKeyChecking=yes), and the file is never written to. Its lines are OpenSSH known_hosts lines; a host on a port other than 22 is written `[host]:port`. When unset (the default), host keys are handled as by the libgit2 fetch. A relative path is taken relative to the server's working directory at start. With SCOPES_GIT_FETCH_WITH_CLI on, the server does not start when this names no readable file or its path holds whitespace; a file that becomes unreadable later fails each SSH fetch at once (counted with reason `local`). With SCOPES_GIT_FETCH_WITH_CLI off it is ignored, and logged at ERROR.

#### OPAL_SCOPES_GIT_MAX_WORKERS

Default: `10`

Maximum number of concurrent scope git operations. It bounds phase 1 (the network clone/fetch of each distinct repo) AND phase 2 (the local change-check of scopes that reuse an already-cloned repo), so it sets how many clones a sync pass syncs at once in either phase. In phase 1 that is one scope per clone. In phase 2 a clone's slot syncs up to 8 of its scopes at once, in lanes of their own: they read their records from the store side by side, and take the clone's sync lock one at a time for the change-check, so up to 8 times this many scopes are in flight, while each clone's git work still runs one scope at a time. A timed-out operation stops counting against this limit, so one hung remote does not hold a concurrency slot — its lingering daemon thread persists on its own (a black-holed remote's can persist for the life of the process). That tail is bounded by SCOPES_GIT_MAX_ZOMBIES, which is a GLOBAL ceiling: read its description, because at that ceiling new git ops are refused for every scope, healthy ones included.

#### OPAL_SCOPES_PURGE_CHANNEL

Default: `__opal_scope_purge__`

Pub/sub channel (worker-to-worker, over the broadcaster) used to purge GitPolicyFetcher caches fleet-wide when a scope is deleted or repointed to a new source. Every worker subscribes and drops its own cache entries; the leader is the only actor that may authorize that, because only it can check whether a surviving scope still shares the source. It does not remove the clone dir.

#### OPAL_SCOPES_GIT_PRELOAD_DRAIN_TIMEOUT

Default: `10.0`

Max seconds the pre-fork scope preload waits for in-flight git ops to finish before tearing down and forking workers. Ops still lingering past this bound are left running on their daemon threads and their cached handles are left unfreed by the pre-fork cache reset, avoiding a use-after-free (0 = don't wait). With SCOPES_GIT_FETCH_WITH_CLI on, the preload's event loop also waits up to this long for git command-line ops still being stopped; those not done by then get SIGKILL as the loop ends, their clones stay recorded as unfinished, and the next op on each clone removes what git left.

#### OPAL_SCOPES_GIT_RECLONE_HUNG_ON_START

Default: `False`

Whether a server start clones again the scope clones on which a git op was still hung when its server process ended. A fetch or clone that runs past SCOPES_GIT_FETCH_TIMEOUT keeps running on its daemon thread, and the clone is not fetched again while it lasts. With this on (and SCOPES_GIT_FETCH_TIMEOUT positive), such an op writes a marker file of its own, with a unique name, in a directory beside the clone (git_sources/SOURCE_ID.hung/, SOURCE_ID being the clone's directory name) and removes it when it returns. A marker whose process ended first (a container restart, or a worker killed mid-op) stays until a fetch or clone of that source succeeds within its timeout, which removes them all; a fetch that fails quickly (revoked credentials, a deleted repository) or succeeds only after its timeout does not remove it. With this off a start removes them all. A container restarted while an op was still hung (by an orchestrator's health check, say) keeps its clones on its volume and would otherwise go back to that clone, while a new pod (empty volume) clones fresh. The pre-fork scope preload, which scripts/gunicorn_conf.py runs in the gunicorn master before any worker exists (as the Docker image does; opal-server run has no preload), deletes every clone with a marker before its sync, so the sync clones it fresh, as on a new pod: if that clone fails or hangs too (the remote is still unreachable), the source has no clone, and its scopes no policy, until a clone succeeds, again as on a new pod. When the marked clones of the current scopes' sources span at least two of the repositories those scopes have a clone of on disk, and at least half of them, the hang is most likely the git provider's and nothing is deleted, so every scope keeps its last fetched policy; nothing is deleted either when no clone on disk is one the current scopes use. Do not share BASE_DIR between running servers with this on: any marker counts, whoever wrote it. Each clone deleted increments opal_server.scopes.hung_clone_recloned.

#### OPAL_SCOPES_GIT_MAX_ZOMBIES

Default: `40`

Maximum number of in-flight scope git operations (live plus lingering timed-out) allowed to hold a daemon thread at once, counted GLOBALLY across all sources. It is a last-resort ceiling on thread growth when remotes hang, not a per-source guard — that is handled separately, by skipping a source that already has an operation in flight. Once the ceiling is reached, new git ops are refused (logged, and retried next cycle) for EVERY scope, healthy ones included, until enough threads drain; with remotes that never return, that state can persist. Set it well above SCOPES_GIT_MAX_WORKERS and alert on the refusal log (0 = no cap; a negative value is clamped to 0 and also means no cap, at the cost of unbounded thread growth during an outage).

#### OPAL_SCOPES_GIT_FETCH_PRUNE

Default: `False`

Whether a scope fetch prunes: a branch deleted on the remote then leaves the clone, so a scope naming it misses instead of being served the deleted branch's last head. Off by default: a pruned fetch compares every local and remote ref, which on a clone with tens of thousands of branches adds seconds per fetch under the lock every scope on that clone shares. With the libgit2 fetch (SCOPES_GIT_FETCH_WITH_CLI off), each ref pruned from a clone whose refs are packed (see SCOPES_GIT_REPACK_PACK_LIMIT) costs more, since libgit2 rewrites the packed-refs file for each one, and that file grows with the repository's branches: about 20 ms per ref on a clone of a repository with 63,000 branches, and about 1 ms with 2,000. Pruning a thousand refs from the larger clone takes tens of seconds, against a couple of seconds with git. Turn SCOPES_GIT_FETCH_WITH_CLI on for large clones that prune. Only `refs/remotes/<remote>/*` are pruned; the scopes' `refs/heads/scopes/*` stay.

#### OPAL_SCOPES_GIT_BACKOFF_BASE_SECONDS

Default: `10.0`

First delay before the periodic sync pass re-attempts a SOURCE whose git clone or fetch just failed (unreachable host, revoked credentials, deleted repo); every further consecutive failure doubles it — 10s, 20s, 40s, ... minutes, hours, days — with no upper bound unless SCOPES_GIT_BACKOFF_MAX_SECONDS is set. A delay shorter than the gap to the next pass simply does not skip that pass, so the first few doublings cost one attempt per pass exactly as before and the schedule bites from roughly the fourth consecutive failure. It exists because nothing else records a failure: without it every pass re-attempts every dead repo, and so does every duplicate scope sharing that repo — a handful of dead repositories can account for thousands of clone attempts per hour. The periodic pass and the boot preload honour it (in both phases, and re-checked under the source lock, so duplicates of a source that fails in a pass cost one attempt, not one per scope), and so does the sync GET /scopes/:scope_id/policy requests for a scope whose branch is missing from its clone (SCOPES_POLICY_BRANCH_REFRESH_INTERVAL); an explicit POST /scopes/:scope_id/refresh, POST /scopes/refresh or PUT /scopes attempts the source immediately, so an operator who has just repaired credentials recovers at once, and any successful clone or fetch clears both the delay and the consecutive-failure count. The state is in-memory and per process — it resets on restart. When a periodic pass runs (POLICY_REFRESH_INTERVAL > 0) a forked worker inherits whatever the pre-fork preload recorded, so the leader does not re-hammer repos that already failed at boot; without one, the boot sync is the only pass-originated sync, so it drops the inherited entries and attempts every source once. Watch opal_server.scopes.sources_in_backoff (gauge of sources currently being skipped, tagged by pid) and opal_server.scopes.git_op_skipped with reason:backoff (counter); the WARNING logged when a source enters backoff, and again when its delay first exceeds a day, names the repository. 0 or negative disables the backoff entirely — nothing is recorded and nothing is skipped; nan and inf are treated as disabled too, because they parse cleanly rather than failing the process at startup and neither is a duration.

#### OPAL_SCOPES_GIT_BACKOFF_MAX_SECONDS

Default: `0.0`

Optional cap on the per-source doubling backoff of SCOPES_GIT_BACKOFF_BASE_SECONDS. 0 (the default), negative, nan or inf means NO cap: a repository that has been unreachable for a day is checked again in two, then four, and before long only at the next restart or explicit refresh — a repository that keeps failing is, in all likelihood, dead. Set a positive value to bound instead how stale a repository that comes back on its own (without anyone touching its scope) can get: the periodic pass then re-attempts it at most that long after the previous attempt. A value below the base is floored at the base (one pass at a time), never inert. Lowering the cap at runtime is not retroactive for delays already armed.

#### OPAL_SCOPES_GIT_REPACK_PACK_LIMIT

Default: `50`

Pack-file count at which a scope clone is repacked: once a successful fetch leaves the clone holding at least this many pack files, git repack -a -d -k runs on it at the end of the sync pass, after the pass has sent its notifications, merging them into a single pack and dropping the duplicate objects. Before it, git pack-refs --all moves the clone's refs, which libgit2 keeps in a file each, into one packed-refs file, and the clone's reflogs, which OPAL never reads, are turned off (core.logAllRefUpdates=false in the clone's config, which new scope clones are made with) and removed (moved aside within the repack's timeout, and deleted once the repack has let go of the clone): with a file of at least one filesystem block per ref, the reflogs of a clone with tens of thousands of branches can take many times the disk of its objects. A clone whose refs are not packed (a fresh libgit2 clone, or one made by an earlier version) gets these ref steps alone at the end of the next sync pass after its clone or fetch, without waiting for the limit. They are counted as opal_server.scopes.git_pack_refs by outcome, with a git_pack_refs_seconds distribution, and a git pack-refs that fails there holds off the clone's repacks for an hour, as a failed repack does. Before a repack, a ref step that fails is a warning and the repack still runs; every ref step that fails, runs past its share of SCOPES_GIT_REPACK_TIMEOUT or leaves the refs in files of their own is counted as opal_server.scopes.git_ref_step_failures, tagged by step (config, reflogs or pack_refs). A refresh of a single scope (POST /scopes/:scope_id/refresh, or a PUT /scopes) repacks its clone right after its own sync, once its notification is out, so it repacks even when no periodic pass runs (POLICY_REFRESH_INTERVAL=0). A pass never waits for a clone another sync or refresh is using: it leaves that clone to the next pass or refresh. No repack starts while a sync pass runs in the same process: the pass that ends last repacks what the others left. Objects no branch reaches any more, those of branches deleted upstream included, are kept in the merged pack rather than deleted, so that a repack never removes an object a fetch in another process is about to point a branch at; the cost is that they stay until the clone is cloned again. It exists because the scopes git fetcher (pygit2 on libgit2) writes one new pack file per fetch and never consolidates them, and a fetch of a repository with many branches can re-download history the clone already has, so without it the clone's disk grows without bound until the volume holding the clones fills. It only affects scopes mode (SCOPES=true): the classic policy-repo path fetches with the git command line, which cleans up its own packs. The git binary must be on PATH (the official images ship it). The repack runs inside the opal-server container, one clone at a time per pod, enforced with an flock on the directory holding the clones: that directory must be on a local filesystem, or on NFS mounted with local_lock=flock, since where flock fails every repack fails and is retried once an hour. Its memory counts against the container's limit: allow about 0.5 KB per object of the repository. On Linux git runs with oom_score_adj 1000, so when the container runs out of memory the kernel picks the repack before an opal-server worker. Where the whole container is the unit of an OOM kill (Kubernetes on cgroup v2, unless the kubelet sets singleProcessOOMKill) the container restarts instead. The repack's attempt marker in the clone then keeps the restarted server from repacking that clone for an hour (plus the repack timeout), so the restarts come at most hourly rather than in a loop, and an INFO line names the clone; they stop only once the memory limit leaves room for the repack. Size it with that room. It needs disk too: git writes the merged pack before it deletes the old ones, so the volume holding the clones needs free space for about one more copy of the clone's packs. On a volume that fills up for real, a repack that runs out of space fails, is logged and is not retried for an hour, and while it writes, fetches of other clones on that volume can fail as well. On a Kubernetes emptyDir with a sizeLimit nothing fails: the kubelet EVICTS the pod (skipping its preStop hook) once the volume passes the limit, so size the limit with room for one more copy of the largest clone's packs above its usual peak. A repack that fails, or never finishes because its process died, is not retried for an hour by any process of the pod, a new leader included. While sync passes keep running back to back, a due repack waits for a gap (each wait counted as opal_server.scopes.git_op_skipped with reason pass_in_flight); once it has waited 30 minutes, the next attempt runs it beside a pass, which can then stall that pass for as long as the repack runs. Raise the limit to repack less often; 0 or negative disables repacking, and 1 counts as 2, since a clone always holds a pack after a fetch.

#### OPAL_SCOPES_GIT_REPACK_TIMEOUT

Default: `120.0`

Hard timeout in seconds for one scope clone repack (see SCOPES_GIT_REPACK_PACK_LIMIT), its git pack-refs included, and for a run of its ref steps alone. Before a repack the ref steps get half of it: past that the one running is stopped, and git repack gets the rest. Unlike SCOPES_GIT_FETCH_TIMEOUT it is HARD: when it expires git gets SIGTERM, then SIGKILL 10 seconds later, the files and locks it left in the clone are removed, and the clone keeps the packs it already had. Stopping git can take up to 20 seconds past the timeout, and OPAL waits for it up to 30 seconds past the timeout, so once git starts the repack holds the clone's sync lock for at most the timeout plus 30 seconds (150 seconds with the default). One case outlives that bound: a git stuck in uninterruptible I/O survives SIGKILL, and keeps the pod-wide repack lock, so no other repack starts in the pod until it exits. A git whose opal-server worker exits mid-repack does not outlive it: git runs under a watchdog that kills its whole process group once that worker is gone. It must stay bounded because the repack holds the clone's sync lock while it runs. Repacks run one at a time at the end of a sync pass, after its notifications, so within one pass a repack delays none of them, and a refresh of a single scope runs its repack right after its own notification. No repack starts while another sync pass runs (the boot sync next to the first periodic pass, or a POST /scopes/refresh), whose syncs would otherwise queue on the clone's lock while holding their SCOPES_GIT_MAX_WORKERS slots and stall the whole pass, every other clone's scopes included; the pass that ends last runs it. A pass that starts while a repack is already running still waits for it in the same way, as it does for a slow fetch. The next periodic pass starts only once the repacks are done. The default leaves several times the time a repack of a clone with tens of thousands of branches takes, most of it CPU; too low a value is worse than too high, since a repack that always times out never reclaims any disk. Watch opal_server.scopes.git_repack with outcome:timeout and the git_repack_seconds distribution. 0, negative, nan or inf fall back to the default of 120 seconds, and a value over 86400 (a day) is capped at 86400 with a warning, because a wait of more than about 24 days overflows and fails every repack; there is no way to set no limit.

#### OPAL_SCOPES_STORE_READ_TIMEOUT

Default: `10.0`

Timeout for a scope-store read taken while holding a source's lock — the sibling check a delete/repoint purge runs before authorizing the fleet-wide cache purge. The Redis client is built without a socket timeout, so without this an unreachable store would pin that lock for the life of the process and block every later sync, purge and delete for the source. On expiry the sibling check fails open, and what that decides is the fleet-wide MEMORY purge only — the leader no longer touches the clone tree: a DELETE confirms it defensively (its record is already gone, so withholding would strand the fleet's cache entries, while over-purging self-heals on the surviving sibling's next sync), a REPOINT withholds it (the old source's record is still live, just moved). The clone dir is unaffected either way: on a store fault the delete floor KEEPS this worker's clone rather than risk deleting one a live sibling shares, leaving an orphan tracked by PER-15612 (0 or negative means no timeout).

#### OPAL_SCOPES_POLICY_CLONE_WAIT_SECONDS

Default: `20.0`

How long GET /scopes/:scope_id/policy holds a request while that scope's clone is still being populated, before falling through to the 503 + Retry-After it answers today. The route re-checks once a second and returns the bundle the moment the clone is usable. It exists because the opal-client PDP ignores Retry-After: it makes five attempts with random-exponential backoff capped at 10s (~20-40s of coverage) and then stays quiet until the next pub/sub policy message or a reconnect, so a clone that outlives those attempts strands that PDP with no policy — and the update-all published when a clone completes names only the scope that was syncing, so siblings sharing the same clone are not woken. Holding the request converts that gap into latency the client already tolerates: five client attempts against a 20s hold cover about two minutes of clone time, so short and medium re-clones — meaning the download phase; the rmtree-and-init window before it answers 503 + Retry-After 5 and is not waited on — produce no client-visible gap. What this bounds is the WAIT plus at most one more bundle attempt: time queued behind other bundle builds on the shared executor is outside the deadline, which is what SCOPES_POLICY_CLONE_WAIT_MAX_INFLIGHT bounds instead. The budget matters in both directions — 20s is well under the 60s ALB idle timeout (a longer hold surfaces as a 504, which the client cannot tell apart from a dead server) and far under the client's 300s aiohttp total timeout. Readiness is derived from DISK (the clone still has no remote-tracking refs), never from an in-process marker, so every worker answers alike: the clone runs in the leader while this route is served by any worker. The hold is an awaited sleep loop, so it occupies no thread between polls and leaves the event loop and the gunicorn worker heartbeat unaffected; it is abandoned early if the client disconnects. 0 or negative disables the wait (answer 503 immediately), and with it the branch wait of SCOPES_POLICY_BRANCH_REFRESH_INTERVAL. nan, inf and -inf are treated as disabled too: unlike a non-numeric value, which fails this process at startup when the environment is parsed, they parse cleanly — inf would otherwise mean the clamped maximum hold on every clone-in-progress request, and nan is not a budget at all. Values above 55s are clamped to 55s so the hold can never outlive the load balancer's idle timeout.

#### OPAL_SCOPES_POLICY_CLONE_WAIT_MAX_INFLIGHT

Default: `64`

Maximum number of requests one worker process may hold at once inside the SCOPES_POLICY_CLONE_WAIT_SECONDS wait. Requests beyond the cap get the immediate answer they would have got before the wait existed (503 + Retry-After 30 for a clone in progress, 409 for a missing branch), so the cap can never make things worse than not waiting. It exists because polling is cheap but RELEASING is not: when the clone lands, every held request builds a full bundle on the loop's DEFAULT executor: about min(32, cpu+4) threads shared by every off-loop call this process makes, in front of an unbounded queue. Measured throughput there falls from ~52 bundles/s at 32 concurrent builds to ~18/s at 1000. Scope git clone/fetch does NOT share that pool — each op runs on its own single-use daemon-thread executor, bounded by SCOPES_GIT_MAX_WORKERS through a semaphore — so this key is the only bound on how many bundle builds can pile up at once. Size it so the cap divided by the bundles-per-second that pod can really build fits inside the 60s ALB idle timeout MINUS the hold: above that, released requests queue past the timeout and 504 — the very failure the hold exists to prevent — and a rolling restart drains worse, because uvicorn waits for in-flight requests while gunicorn SIGKILLs the worker at 30s, dropping every websocket that worker still holds. The count is per process, not per pod: a pod running N workers holds up to N times this number. 0 or negative means no cap.

#### OPAL_SCOPES_POLICY_BRANCH_REFRESH_INTERVAL

Default: `0.0`

Off by default (0): set it, for example to 60, to enable it. When GET /scopes/:scope_id/policy finds the scope's clone populated but without the scope's branch, or finds no clone of the scope's repository at all, this worker asks every server to sync that scope and holds the request in the SCOPES_POLICY_CLONE_WAIT_SECONDS wait, under the same in-flight cap, polling that one branch ref and serving the bundle as soon as the branch is there. The sync is not forced: a server fetches only when its own clone lacks the branch. A branch pushed after a server's last fetch is not a misconfiguration: right after a PUT /scopes that moves a scope to another repository, every pod answers this way until its own fetch of that repository lands, and a pod that missed the PUT's broadcast, or whose fetch failed, keeps answering it until something else syncs that clone. An opal-client that starts in that window makes five attempts, then waits for the next policy message, with no policy loaded. Each worker process requests that sync at most once per this many seconds per scope and branch (a scope that a PUT moves to another repository or branch asks again), and, for a clone it finds missing, once per clone, whichever of the clone's scopes ask: one sync clones it for all of them. Further misses on that worker while its request is younger than the clone wait are held too, without asking again, until the first hold's deadline; after that, for the rest of the interval, a miss gets the immediate 409 (503 with no clone) it got before. A request shed at the in-flight cap requests nothing; a request that requests the sync holds its slot while it does. So a branch that really does not exist costs, per interval, at most one clone-wait budget of held requests on each worker that sees a miss (bounded by the in-flight cap), and one sync request from each of those workers to every server. Every server's clone lacks a branch that does not exist, so each server fetches once per sync request, except that requests reaching a server before its next fetch of that repository starts share that fetch: requests that arrive together cost one or two fetches, while requests spread over the interval (one client's retries usually reach different workers seconds apart) cost one each, under the lock every scope on that clone shares; a server whose clone has the branch does not fetch. Weigh that before turning this on for a clone with tens of thousands of branches. These syncs honour the source's failure backoff, so they do not retry a repository whose fetches keep failing; a server whose fetch has just failed fetches the branch only for a request that arrives after that backoff (SCOPES_GIT_BACKOFF_BASE_SECONDS) has passed. A branch pushed after the fetch a request asked for is not fetched for that scope until a miss after the interval asks again, or something else syncs it: a writer that pushes a scope's branch after its PUT /scopes should refresh the scope (POST /scopes/:scope_id/refresh) after the push. An interval no longer than SCOPES_POLICY_CLONE_WAIT_SECONDS asks again at the first miss after each hold. When the wait runs out with the branch still missing, the answer is that same 409 (a 503 + Retry-After 5 when there is still no clone). 0 or negative disables it (409 or 503 immediately, as before); nan, inf and -inf are treated as disabled too. Requires SCOPES_POLICY_CLONE_WAIT_SECONDS > 0: with that wait disabled, no sync is requested either.

### Broadcasting Configuration

#### OPAL_BROADCAST_URI

Default: `None`

URI for the broadcast backend (Redis, PostgreSQL, etc.).

**Postgres TCP keepalive (opal-server ≥ 0.9.9-rc.3 / `permit-broadcaster` ≥ 0.2.7):** the Postgres backend enables TCP keepalive on every backbone connection by default (idle 30 s, interval 10 s, 3 lost probes → a silently vanished server — e.g. an RDS Multi-AZ failover — is detected within ~60 s instead of never). It can be tuned or disabled with libpq-style parameters in the URI: `postgres://…/db?keepalives=1&keepalives_idle=30&keepalives_interval=10&keepalives_count=3` (`keepalives=0` disables).

:::danger version constraint
Only set `keepalives*` parameters when **every** opal-server that shares this URI runs ≥ 0.9.9-rc.3. Earlier versions (`permit-broadcaster` ≤ 0.2.6) forward these parameters to Postgres as session settings, and Postgres rejects the connection with `FATAL: unrecognized configuration parameter` — a pod rolled back (or a canary slice still on the old image) would have **zero backbone connectivity while its health checks stay green**. The defaults require no URI change at all; only add the parameters once the fleet is uniformly upgraded.
:::

**Connection budget (Postgres backend):** each worker process that holds a backbone reader opens a connection *pool*: 10 connections at boot (asyncpg's default `min_size`, not configurable downward via `BROADCASTER_PG_MAX_POOL_SIZE`, which only raises the ceiling), decaying to ~1 idle connection after ~300 s. Size the broadcast database's `max_connections` for **10 × workers × pods during a rolling restart**, not for the steady state.

For more information, see [running OPAL with Kafka](/tutorials/run_opal_with_kafka) and [running OPAL with Apache Pulsar](/tutorials/run_opal_with_pulsar).

#### OPAL_POLICY_STORE_CONN_RETRY

Default: `{"wait_strategy": "fixed", "wait_time": 2, "attempts": 2}`

Retry options when connecting to the policy store (i.e., the agent that handles the policy, e.g., OPA). Keys: `wait_strategy` (`fixed`, `exponential` or `random_exponential`), `wait_time` in seconds, `attempts`, and `max_wait`, the most to wait between attempts with an exponential strategy (no limit by default).

#### OPAL_POLICY_STORE_LIVENESS_PROBE_ENABLED

Default: `True`

If enabled, OPAL Client periodically probes the policy store's health endpoint
in a background task and factors the result into the `/healthy` HTTP response.

Without this probe, `/healthy` reflects only the success of the last
`server -> policy-store` transaction, which can stay `True` even if OPA hangs,
deadlocks, or stops accepting HTTP connections in steady state. With it
enabled, supervisors that probe `/healthy` will see the client report unhealthy
within one probe interval if the policy store becomes unresponsive, and
recover automatically once it returns.

The `/healthy` endpoint itself remains O(1): the probe runs once per interval
in the background and updates a cached flag — high-frequency `/healthy`
polling does not translate into proportional load on the policy store.

#### OPAL_POLICY_STORE_LIVENESS_PROBE_INTERVAL_SECONDS

Default: `10`

Interval (in seconds) between background liveness probes against the policy store.

#### OPAL_POLICY_STORE_LIVENESS_PROBE_TIMEOUT_SECONDS

Default: `2`

Per-request HTTP timeout (in seconds) for liveness probes against the policy
store. A probe that exceeds this timeout is treated as an unreachable sample.

#### OPAL_POLICY_STORE_POLICY_PATHS_TO_IGNORE

Default: `[]`

Which policy paths pushed to the client should be ignored. List of glob-style paths, or paths without wildcards but ending with "/**" indicating a parent path (ignoring all under it). Supports paths starting with '!' to force not ignoring them: a negated path always takes precedence.

#### Configuration Architecture

OPAL's configuration is based on our very own `Confi` module, which in turn is based on [Decouple](https://pypi.org/project/python-decouple/), and adds complex value parsing with Pydantic, and command line arguments via Typer/Click.
