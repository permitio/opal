# Monitoring OPAL

There are multiple ways you can monitor your OPAL deployment:

- **Logs** - Using the structured logs outputted to stderr by both the OPAL-servers and OPAL-clients
- **Health-checks** - OPAL exposes HTTP health check endpoints ([See below](#health-checks))
- [**Callbacks**](/tutorials/healthcheck_policy_and_update_callbacks#-data-update-callbacks) - Using the callback webhooks feature - having OPAL-clients report their updates
- **Statistics** - Using the built-in statistics feature in OPAL ([See below](#opal-statistics))
- **Metrics** - DogStatsD metrics, among them those of the scope clones' git operations ([See below](#scope-git-metrics))
- **DataDog APM** - OPAL supports DataDog APM tracing (requires ddtrace v4.8.2+; OPAL itself requires Python 3.14)

## Health checks

### OPAL Server

opal-server serves these health routes. None of them contacts a git remote, Redis or the broadcaster's backbone: each reads the worker's own state and files on its disk, so a remote or Redis that is down fails none of them. Nor does a backbone that is down, for as long as the reconnecting broadcaster's reader keeps retrying, which by default (`OPAL_BROADCAST_RECONNECT_MAX_RETRIES=0`) is for good; with a reconnect budget it can give up (see below). Under gunicorn a probe reaches whichever worker of the pod accepts it; what the scopes leader reports is in a file every worker reads.

| Route | For | Answers `503` |
| --- | --- | --- |
| `/` | | Never: `200 OK` while the process serves. |
| `/healthz/live` | liveness | When the worker's broadcaster reader gave up (after [`OPAL_BROADCAST_RECONNECT_MAX_RETRIES`](/getting-started/configuration#opal_broadcast_reconnect_max_retries)) or died while clients listen, with [`OPAL_BROADCAST_HEALTHCHECK_ENABLED`](/getting-started/configuration#opal_broadcast_healthcheck_enabled) (`"failed": ["broadcaster"]`); and in scopes mode with the watcher on ([`OPAL_REPO_WATCHER_ENABLED`](/getting-started/configuration#opal_repo_watcher_enabled)), when the scopes leader's heartbeat is missing or more than 300 seconds old (`"failed": ["leader"]`). The body is `{"status": "error", "failed": [...]}`. |
| `/healthz/started` | startup | Until the worker has started (`"worker"`); in scopes mode with the watcher on, until the leader has written a heartbeat since then (`"leader"`); and until every clone of the repositories in [`OPAL_SCOPES_READY_REQUIRED_REPOS`](/getting-started/configuration#opal_scopes_ready_required_repos) has landed (`"clones"`). The body is `{"status": "starting", "waiting_for": [...]}`. Once it has answered `200`, it answers `200` for the life of the worker. |
| `/healthcheck` | readiness | While the worker's broadcaster reader is wedged (`{"status": "error", "broadcaster": "unhealthy"}`); in scopes mode with the reconnecting broadcaster, until the worker's own backbone subscription, which fleet purges reach it through, has started, and for good on a worker where it failed to start (`"pubsub": "no backbone subscription"`), both with `OPAL_BROADCAST_HEALTHCHECK_ENABLED`; when the WebSocket pub/sub route `/ws` is not mounted (`"pubsub": "not mounted"`); and in scopes mode until every clone of the repositories in `OPAL_SCOPES_READY_REQUIRED_REPOS` has landed, naming the missing clones' directories (`{"status": "error", "scopes": "clones missing", "missing": [...]}`). Once a worker has seen those clones landed, a fetch that fails or a remote that is down does not fail it again. |

With [`OPAL_BROADCAST_RECONNECT_MAX_RETRIES`](/getting-started/configuration#opal_broadcast_reconnect_max_retries) above 0, a long backbone outage makes the reader give up: once that many reconnects in a row have failed, waiting [`OPAL_BROADCAST_RECONNECT_BACKOFF_MIN_SECONDS`](/getting-started/configuration#opal_broadcast_reconnect_backoff_min_seconds) (0.5) doubling to [`OPAL_BROADCAST_RECONNECT_BACKOFF_MAX_SECONDS`](/getting-started/configuration#opal_broadcast_reconnect_backoff_max_seconds) (30) between them, with jitter. With those defaults, 10 retries take one to two minutes plus each connect attempt. The worker then answers `503` on `/healthz/live` (`"failed": ["broadcaster"]`) and `/healthcheck` (`"broadcaster": "unhealthy"`), and restarts itself; the new worker counts its retries from 0, and gives up the same way while the backbone stays down. With the default 0, a backbone outage fails no probe. `OPAL_BROADCAST_HEALTHCHECK_ENABLED=false` takes the broadcaster out of both routes.

The scopes leader is the worker that holds the leadership lock and runs every git operation. From the moment it takes the lock, before it reads Redis or runs git, and every 10 seconds, it writes `scopes-leader.heartbeat` in [`OPAL_BASE_DIR`](/getting-started/configuration#opal_base_dir) (JSON: `pid`, `at`, and `last_attempt_at` and `last_attempt`, `ok` or `failed`, for its last sync pass or scope refresh) and sends `opal_server.scopes.leader`. It runs on a task of its own, which never waits for a git operation: a clone that runs up to [`OPAL_SCOPES_GIT_CLONE_TIMEOUT`](/getting-started/configuration#opal_scopes_git_clone_timeout), or a sync waiting for one, never delays it. It stops writing when its event loop is blocked, and while a git command-line operation is still awaited 40 seconds past its own timeout ([`OPAL_SCOPES_GIT_FETCH_TIMEOUT`](/getting-started/configuration#opal_scopes_git_fetch_timeout), or the clone timeout for a clone) plus [`OPAL_SCOPES_GIT_CLI_KILL_GRACE`](/getting-started/configuration#opal_scopes_git_cli_kill_grace), by when git has been stopped (a WARNING says so); an operation with no timeout never stops it. Fetches that fail never stop it, and neither does Redis: with [`OPAL_POLICY_REPO_URL`](/getting-started/configuration#opal_policy_repo_url) set, the new leader first stores the default scope in Redis, each try within 10 seconds, and while Redis refuses or does not answer it logs an ERROR and tries again (from 0.5 seconds, doubling to 30), syncing nothing until it is stored. When the leader's worker restarts, another worker takes the lock within seconds and writes again; the 300 seconds cover that.

How fresh the clones are is not a probe: liveness does not restart a pod whose fetches fail (the git command line ends a hung fetch itself). The [fetch metrics](#scope-git-metrics) report each clone's fetch age and failures; alert on them.

#### Kubernetes probes

```yaml
startupProbe:
  httpGet:
    path: /healthz/started
    port: 7002
  periodSeconds: 10
  failureThreshold: 60 # 10 minutes: size it, see below
livenessProbe:
  httpGet:
    path: /healthz/live
    port: 7002
  periodSeconds: 30
  timeoutSeconds: 5
  failureThreshold: 4
readinessProbe:
  httpGet:
    path: /healthcheck
    port: 7002
  periodSeconds: 10
```

Kubernetes runs the readiness and liveness probes only once the startup probe has passed. The startup probe's budget (`periodSeconds` times `failureThreshold`) is what a new pod gets for the pre-fork scope preload and the first clones of `OPAL_SCOPES_READY_REQUIRED_REPOS`: about twice a measured clone of the largest required repository, and below the Deployment's `progressDeadlineSeconds`. With the liveness probe above, a pod whose leader stopped is restarted about two minutes after its heartbeat turned 300 seconds old. These routes are new in this release: roll the probes back together with the image, since an image without `/healthz/started` fails every pod's startup probe.

Probes that read the clones' `FETCH_HEAD` files keep working, but under them a new pod is Ready before its first clones land; see [readiness and the first clones](/overview/scopes#readiness-and-the-first-clones).

### OPAL Client

opal-client exposes 2 types of http health checks:

- **Readiness** - available on `/ready`. <br/>
  Returns `200 OK` if the client have loaded policy & data to OPA at least once (from either server, or local backup file), otherwise `503 Unavailable` is returned.

- **Liveness** - available on `/`, `/healthcheck` & `/healthy`. <br/>
  Returns `200 OK` if the last attempts to load policy & data to OPA were successful, otherwise `503 Unavailable` is returned

**Notice:** if you don't except your opal-client to load any data into OPA, set `OPAL_DATA_UPDATER_ENABLED: False`, so opal-client could report being healthy.

You can also configure opal-client to store dynamic health status as a document in OPA, [Learn more here](/tutorials/healthcheck_policy_and_update_callbacks)

## OPAL Statistics

By enabling `OPAL_STATISTICS_ENABLED=true` (on both servers and clients), the OPAL-Server would start maintaining a unified state of all the clients and which topics they've subscribed to.
The state can then be retrieved as a JSON object by calling the `/statistics` api route on the server

### Code Reference:

- [opal_server/statistics.py](https://github.com/permitio/opal/blob/master/packages/opal-server/opal_server/statistics.py)

## Missing scope metrics

Sent by opal-server in scopes mode for a request of a scope that is not stored
(see [A missing scope](/overview/scopes#a-missing-scope)).

| Metric | Type | Tags | What it counts |
|---|---|---|---|
| `opal_server.scopes.missing_scope` | count | `route`: `policy`, `data` | A `GET /scopes/<scope_id>/policy` or `GET /scopes/<scope_id>/data` for a scope that is not stored, whatever [`OPAL_SCOPES_MISSING_SCOPE`](/getting-started/configuration#opal_scopes_missing_scope) answers. Not tagged with the scope: the WARNING logged with each (`Requested scope <scope_id> not found, ...`) names it. |
| `opal_server.scopes.missing_scope_webhook` | count | `outcome`: `sent`, `rejected`, `timeout`, `failed`, `shed`, `error` | A report of a missing scope to [`OPAL_SCOPES_MISSING_SCOPE_WEBHOOK_URL`](/getting-started/configuration#opal_scopes_missing_scope_webhook_url). `sent`: it answered 2xx; `rejected`: it answered another status; `timeout`: no answer in 5 seconds; `failed`: no connection, or another error of the request; `shed`: 100 POSTs of the worker were under way, so none was sent (a later request for the scope posts it); `error`: a fault of the server's own, logged at ERROR. None is retried. |

## Scope git metrics

With `OPAL_ENABLE_METRICS=true`, opal-server sends DogStatsD metrics to the agent at `DD_AGENT_HOST` (default `localhost`), port 8125, with `permit.opal.` before each name. In scopes mode (`OPAL_SCOPES=true`), these count what happens to the git operations on the scope clones:

| Metric | Type | Tags | What it counts |
| --- | --- | --- | --- |
| `opal_server.scopes.git_op_failures` | count | `op`: `fetch`, `clone`<br/>`reason`: `timeout`, `git_error`, `host_key`, `local` | A fetch or clone of a scope's repository that failed. `timeout`: it ran past [`OPAL_SCOPES_GIT_FETCH_TIMEOUT`](/getting-started/configuration#opal_scopes_git_fetch_timeout) (a clone with the git command line: [`OPAL_SCOPES_GIT_CLONE_TIMEOUT`](/getting-started/configuration#opal_scopes_git_clone_timeout)); `git_error`: git or libgit2 reported an error; `host_key`: the git host's SSH key is not the one recorded for it, or not in [`OPAL_SCOPES_GIT_SSH_KNOWN_HOSTS`](/getting-started/configuration#opal_scopes_git_ssh_known_hosts) (the ERROR logged with it names the file to reset). All three back the source off ([`OPAL_SCOPES_GIT_BACKOFF_BASE_SECONDS`](/getting-started/configuration#opal_scopes_git_backoff_base_seconds)). `local`: a failure on the server's own side, such as an unreadable [`OPAL_SCOPES_GIT_SSH_KNOWN_HOSTS`](/getting-started/configuration#opal_scopes_git_ssh_known_hosts) with either backend, no ssh-keyscan for libgit2 to record an SSH host's key with, or, with [`OPAL_SCOPES_GIT_FETCH_WITH_CLI`](/getting-started/configuration#opal_scopes_git_fetch_with_cli) on, no git, a clone that cannot be set up or a filesystem that refuses the clone's lock. It does not back the source off, unless the source's URL or credentials cannot be given to git. |
| `opal_server.scopes.git_op_skipped` | count | `reason`: `backoff`, `clone_busy`, `repack_running`, `pass_in_flight`, `clone_unreadable` | A git operation that did not run. `backoff`: a sync of the boot, periodic or pre-fork preload sync pass, or of the pass after a backbone gap (not of a pass that serves a `POST /scopes/refresh`), or one that a policy bundle request asked for, while its source is backed off. `clone_busy`: another git operation holds the clone's lock (the file `.<source id>.lock` beside the clone), so a fetch or clone with `OPAL_SCOPES_GIT_FETCH_WITH_CLI` on is skipped, a due repack waits for a later pass, and a clone that has to be removed to be cloned again is left as it is. `repack_running`: a due repack that did not start because another repack runs in the pod. `pass_in_flight`: a due repack put off while a sync pass runs in the same process. `clone_unreadable`: a sync that could not open its scope clone for a reason of the server's own side (too many open files, a permission on the clone's files): the clone is kept and the next sync tries again. |
| `opal_server.scopes.clone_deletions` | count | `reason`: `invalid`, `missing_object` | A scope clone deleted to be cloned again. `invalid`: opening it says it is not a repository, or is corrupt (a config git cannot parse, say). `missing_object`: its refs are there but the commit its branch names is gone. An error of the server's own side while opening a clone (too many open files, a permission) never deletes it: the sync is skipped with a WARNING naming the clone (`git_op_skipped` with reason `clone_unreadable`), and the next sync tries again. |
| `opal_server.scopes.leader` | gauge | | 1, every 10 seconds, from the scopes leader of each pod (with [`OPAL_REPO_WATCHER_ENABLED`](/getting-started/configuration#opal_repo_watcher_enabled) on), with its heartbeat ([health checks](#opal-server)). A pod that sends none has no leader: nothing syncs its scopes. |
| `opal_server.scopes.repo_fetch_age_seconds` | gauge | `repo`: the first 12 hex digits of the clone's directory name in `git_sources` (the sha256 of the repository URL as the scopes write it)<br/>`shard`: the number after its `-` | Every 30 seconds, from the leader, for each scope clone: the seconds since its `FETCH_HEAD` file changed. With the git command line, that is the clone's last fetch or clone that succeeded, of whatever branches. Not sent for a clone with no `FETCH_HEAD`. A clone no stored scope uses any more (a deleted or repointed scope's, or libgit2's `-1` and `-2` shard clones after a switch to the git command line) is fetched by nothing, so its age only grows until it is removed. |
| `opal_server.scopes.repo_fetch_failures` | gauge | as for `repo_fetch_age_seconds` | Every 30 seconds, from the leader, for each scope clone, and for each source whose clone never landed: its fetches and clones in a row that failed for a reason that backs the source off (`git_op_failures` reasons `timeout`, `git_error` and `host_key`, and a source whose URL or credentials cannot be given to git), counted with the backoff off too; 0 after one succeeds. Kept in the leader's memory: a new leader starts from what the pre-fork scope preload counted. |
| `opal_server.scopes.ready_clones_missing` | gauge | `pid` | Sent by `/healthcheck` with [`OPAL_SCOPES_READY_REQUIRED_REPOS`](/getting-started/configuration#opal_scopes_ready_required_repos) set: how many of the required clones the worker has not yet seen landed. 0 once it is Ready. |
| `opal_server.scopes.hung_clone_kept` | count | | A clone with a hung-op marker that a start kept ([`OPAL_SCOPES_GIT_RECLONE_HUNG_ON_START`](/getting-started/configuration#opal_scopes_git_reclone_hung_on_start)): its repository is a required one and the clone had landed. |
| `opal_server.scopes.git_repack` | count | `outcome`: `ok`, `timeout`, `error`, `git_missing` | A repack of a scope clone ([`OPAL_SCOPES_GIT_REPACK_PACK_LIMIT`](/getting-started/configuration#opal_scopes_git_repack_pack_limit)), its ref steps included. `git_missing` is counted once per process, here or in `git_pack_refs`, the first time a repack finds no git. |
| `opal_server.scopes.git_repack_seconds` | distribution | `outcome`: `ok`, `timeout`, `error` | How long a repack held the clone: its ref steps, any wait for a git worker thread, and the walks of the clone's refs and reflogs that size its log line included (for `ok`, the walks before and after git; otherwise the one before). The walks are not bounded by [`OPAL_SCOPES_GIT_REPACK_TIMEOUT`](/getting-started/configuration#opal_scopes_git_repack_timeout), so this can exceed it. |
| `opal_server.scopes.git_pack_refs` | count | `outcome`: as for `git_repack` | A run of the repack's ref steps alone, on a clone that holds fewer packs than the repack limit and has refs to pack (with the libgit2 fetch pruning, reflogs to remove). |
| `opal_server.scopes.git_pack_refs_seconds` | distribution | `outcome`: `ok`, `timeout`, `error` | How long such a run held the clone, measured as for `git_repack_seconds`. |
| `opal_server.scopes.git_ref_step_failures` | count | `step`: `config`, `reflogs`, `pack_refs` | A ref step, in a repack or in a run of its own, that failed, ran past its share of [`OPAL_SCOPES_GIT_REPACK_TIMEOUT`](/getting-started/configuration#opal_scopes_git_repack_timeout), or left refs in files of their own. Before a repack, a failed ref step is a warning and the repack still runs. |
| `opal_server.scopes.policy_fresh_fetch` | count | `outcome`: `fetched`, `failed`, `timeout`, `disconnected`, `cancelled`, `shed`, `published_failed` | A policy bundle request with no `base_hash` (a client with no policy yet) that waited for this server's fetch of the scope's branch ([`OPAL_SCOPES_POLICY_FRESH_FETCH_WAIT_SECONDS`](/getting-started/configuration#opal_scopes_policy_fresh_fetch_wait_seconds)), by how the wait ended. `fetched`: a fetch of the branch that started after the sync request the wait held for succeeded (a request that arrived while that fetch was running takes it too); `failed`: such a fetch failed at the remote, or one failed within the wait before the request (answered at once, with no sync request), or this server's sync gave up on fetching (the source in backoff, a git operation still running); `timeout`: the wait ran out, and the clone's head was served, or a 503 for a branch the clone lacks; `disconnected`: the client left; `cancelled`: the request was; `shed`: no slot of `OPAL_SCOPES_POLICY_CLONE_WAIT_MAX_INFLIGHT` was free, or too many sync requests were still being published; `published_failed`: the sync could not be requested (also for the requests that rode it). The last two serve the bundle without waiting. |
| `opal_server.scopes.policy_fresh_fetch_seconds` | gauge | `outcome`: as for `policy_fresh_fetch` | How long such a request waited. |

Monitors to start from:

- The main repository's `repo_fetch_age_seconds`, with the git command line on `shard:0` (its one clone), above 1800 for 10 minutes, on any pod: its clone has not fetched for 30 minutes. Alert on the repositories whose scopes refresh often only: a quiet repository with no refreshes ages without being wrong.
- Any `repo_fetch_failures` at 5 or more.
- No `opal_server.scopes.leader` from a pod for 5 minutes.

A repository's `repo` tag is the start of the sha256 of its URL: `printf %s '<URL>' | sha256sum | cut -c1-12`.

## DataDog APM Monitoring

OPAL supports DataDog APM (Application Performance Monitoring) for observing your OPAL deployment's performance and traces.

### Requirements

- **ddtrace v4.8.2 or higher, below 5** - 4.8.2 is the first release with the fix for CVE-2026-50271 (GHSA-mw54-j2v2-42hr)
- **Python 3.14** - the one Python OPAL supports (ddtrace v4 itself supports 3.9+)

### Configuration

To enable DataDog APM monitoring:

1. Set the `ENABLE_DATADOG_APM=true` environment variable for both OPAL server and client
2. (Optional) To disable APM when needed, set `DD_TRACE_ENABLED=false`

### Breaking Changes in ddtrace v3.0.0

The following changes were made to support ddtrace v3.0.0:

- The `ddtrace.filters.TraceFilter` import has been moved to `ddtrace.trace.TraceFilter`
- Programmatic APM disabling via `tracer.configure(enabled=False)` is no longer supported
- APM should now be disabled using the `DD_TRACE_ENABLED=false` environment variable

For more information about ddtrace v3.0.0 changes, see the [official migration guide](https://github.com/DataDog/dd-trace-py/releases/tag/v3.0.0).

### ddtrace v4

ddtrace v4 traces every websocket message by default; v3 did not. OPAL's pub/sub runs over websockets, so that would turn each published update into spans. OPAL keeps the v3 behaviour: the Docker images set `DD_TRACE_WEBSOCKET_MESSAGES_ENABLED=false`, and `configure_apm` applies the same default to the ASGI, Starlette and FastAPI integrations when neither `DD_TRACE_WEBSOCKET_MESSAGES_ENABLED` nor the older `DD_ASGI_TRACE_WEBSOCKET` is set, including under `ddtrace-run`. Set `DD_TRACE_WEBSOCKET_MESSAGES_ENABLED=true` to trace websocket messages; in the Docker images it is the only variable that does, since the image's own setting takes precedence over the older name.

OPAL uses none of the APIs v4 removed (`Pin`, `Span.set_tag_str`, `ddtrace.settings`, the `opentracer` package and others); its only v4-specific change is the websocket default above. If you import ddtrace yourself next to OPAL, for example from a custom fetch provider, check your own code against the [v4.0.0 release notes](https://github.com/DataDog/dd-trace-py/releases/tag/v4.0.0).


## OPAL Client tracker (EAP)

Alternative implementation for the Statistics feature, OPAL-Server tracks all OPAL-clients connected through websocket.
Gathered information includes connection details (client's source host and port), connection time, and subscribed topics.
Available through `/pubsub_client_info` api route on the server.

### Caveats:
- When `UVICORN_NUM_WORKERS > 1`, retrieved information would only include clients connected to the replying server process.
- The values of query parameters with auth-like names (e.g. `token`, `api_key`, `password`) in a client's websocket URL are reported as `***`.
- This is an early access feature and is likely to change. Backward compatibility is not garaunteed.
